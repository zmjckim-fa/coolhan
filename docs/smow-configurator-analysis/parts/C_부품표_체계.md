대상: https://www.smow.de/konfigurator/usm/haller 의 공개 JS (읽기 전용 정적 분석, 코드 실행 없음)
분석 파일: `14xezdwz4pjta.js`(정리본), `0sqfjbgv28kbx.js`(상수), `13lzs0_g8pri-.js`(금고·색), `0pv910lfhfhfu.js`(UI)
줄 번호는 모두 정리본 기준이다. 약어 `14x`는 `14xezdwz4pjta.js`.

증거 등급: **SOURCE**(코드에 그대로 있음, 줄 번호 병기) / **PARTIAL**(코드 일부에서 도출, 나머지는 추정) / **GUESS**(추정).
등급 표기가 없는 항목은 GUESS다.

**가격 취급 원칙.** 판매 단가(EUR/CHF)와 재고 수량은 기록하지 않았다. 가격은 "존재, 형식, 건수"만 적는다. 무게(W)와 치수는 사양값이라 기록했다.

```

## 1. 표별 정리

공통 사항
- 치수 단위는 cm. 허용 값은 `17.5 / 25 / 35 / 50 / 75` 다섯 가지 (파이프·패널 기하 정의 `sM.geometries` 키, 14x:16135~16170 — SOURCE).
- 두 치수를 받는 표(패널, 문, 선반)는 호출 함수가 `큰 값, 작은 값` 순으로 정렬해 조회한다. 정렬하지 않는 표는 아래 "키 순서" 열에 적었다.
- `W`는 그램(g). 근거: `MAX_WEIGHT: 8e4`가 80 kg이고 `weightKg = weight/1000` (14x:22850대, 0sqfjbgv28kbx.js:838~840) — SOURCE.
- `A`는 smow 내부 숫자 키(= 공급사 USM 소매 품번과 동일 계열로 보이나 확인 불가, GUESS). 아래 표의 "항목 수"는 말단 `{A, W}` 개수.

호출 의미 주의 (SOURCE 14x:22579~22602)
- 왼쪽 옆판: 왼쪽 열에 같은 높이 칸(`w`)이 없으면 `lw`(닫힌 `o$`). 있으면 그 칸의 오른쪽(실제 코드는 LEFT) 옆판이 비어 있을 때만 `lR`(구멍 `o3`)로 1장 추가하고, 이미 있으면 추가하지 않는다. 오른쪽 옆판은 오른쪽 열의 같은 높이 칸이 있으면 `lR`, 없으면 `lw`. 즉 **이웃과 맞닿는 옆판은 구멍판, 바깥 옆판은 닫힌 판**이다. PARTIAL — 변수 의미는 코드(`w=e[t-1].elements[e]`, `C=e[t+1].elements[e]`)에서 도출, 화면상 의미는 추정.

- 부품 표에서 참조되는 키는 98개이고, 단가표에는 6개가 더 있다: `10731, 10737, 11205, 16170, 16174, 16634`. 이 6개는 어떤 `o*` 표에도 없고 이름표(`lo`)에도 없다. 품번은 있다(`UH 052 001/009/003`, `UH 054 009/006/004`). 판매 중단 품목이거나 구성기가 쓰지 않는 파이프·패널일 가능성 (GUESS).
- **단가는 색과 무관하다.** 색 키(`11203.22`)로 단가를 찾지 않고 `A`(`11203`)로 찾는다.
- 조립 서비스료: `lc`/`lu`에 `ASSEMBLE_PRICE_PERCENTAGE`(비율)와 `ASSEMBLE_PRICE_SERVICE_COSTS`(고정금액)가 있고 `조립료(순) = 순합계 × 비율 + 고정금액`으로 계산된다 (14x:22889~22896, SOURCE). 값은 기록하지 않았다.
- 모든 단가는 부가세 제외(net)로 보인다. 근거: `priceGross = floor(price × i)`, `i`는 `1 + 부가세율/100` (14x:342~345 부근, 22862~, PARTIAL). 총액은 **정수로 내림**(`Math.floor`) 한다는 점이 우리 계산과 다를 수 있다 (SOURCE 14x:22862~22868).

## 2. 품번 체계

### 2-1. 키 → 품번 규칙 (SOURCE)

```
키 = 색 없는 부품: String(A)                  예) "10751"      → oP["10751"]    = "UH 058 000"
키 = 색 있는 부품: String(A) + oG[색ID].A     예) "11203.22"   → oP["11203.22"] = "UH 053 043"
품번 = oP[키]   (없으면 undefined)

- `oP` 총 616개 = 색 없는 31 + 색 있는 585 (39 기본키 × 15색). 585개 = 정확히 39 × 15, 빠진 색 없음 (grep 집계로 확인).

- `artNum`이 없으면(`undefined`) 재고 확인에서 "No smow article number" 오류 로그를 남기고 **빠른 배송(FAST) 판정에서 제외**한다 (14x:21311~21350, SOURCE).

| `lc[A]`/`lu[A]` 없음 | 예외 없이 `undefined` → 금액이 `NaN` (가격 오염) |
| `oP[키]` 없음 | 예외 없음. `artNum = undefined`; 재고 판정에서 "No smow article number" 로그 후 NORMAL 배송 |
| `balzSafeArticleNumber`가 undefined | 금고 항목 건너뜀 (14x:22143) |
| `safeVariant(품번)`이 undefined | 오류 로그 후 금고 가격 0으로 계산 (14x:22144~22146) |
| 재고 맵에 해당 품번 없음 | "No stock info" 로그, FAST 불가 |
| 재고 맵 로딩 실패 | 최대 4회 재시도 뒤 포기하고 로그 (14x:38406~) |

→ 우리 구현에서는 위의 `TypeError`와 `NaN`을 **표 로드 시점의 정합성 검사**(키 존재, 단가 존재, 품번 존재)로 미리 잡는 편이 안전하다.

### 4-3. 열 처리와 조립용 교체 (PARTIAL)

- 큰 구성(열 무게 > 80000 g이거나 높이 > 200 cm)은 일부 높이 파이프를 `o8` 슬롯 파이프로 교체하고, 교체 수 × 2 만큼 커넥터를 차감한다. 교체 위치 선택(3번째마다, 17.5 cm는 이웃으로 대체)은 14x:22757~22790에 있으나 정확한 분배 공식은 해독하지 못했다. 우리 시스템에서는 **그대로 따라 할 필요 없이 "무게·크기 초과 시 슬롯 파이프 사용"이라는 규칙만 둔다** 해도 공급사 부품표와는 어긋날 수 있다. GUESS.
- 확장 도어 겹침: 세로 간격 > 30 이면 35 cm 보강봉, > 20 이면 25, > 15 이면 17.5 를 2개씩, 스토퍼 2개 + 보강봉 개수만큼 추가 스토퍼 (14x:22731~22750, SOURCE).

### 5-1. 금고(Balzsafe) — 품번 체계 (SOURCE, 13lzs0_g8pri-.js:668~783)

| 항목 | 값 |
|---|---|
| 접두사 `SAFE_ARTNUM_PREFIX` | `"BZ 002 "` |

| 기본 색 `SAFE_DEFAULT_COLOR_ID` | 33 (anthrazitgrau) |
| 기본 잠금 `SAFE_DEFAULT_LOCK` | `"electronic"` |
| 잠금 종류 | `electronic`(전자 번호), `key`(열쇠) |

`balzSafeArticleNumber(깊이, 색ID = 33, 잠금 = "electronic")` = 표 `i["깊이|색|잠금"]`. 표는 **정확히 60개**: 2(깊이 35/50) × 15색 × 2(electronic/key).

번호 규칙:
- 깊이 35는 `BZ 002 001`~`030`, 깊이 50은 `031`~`060` (깊이 50 = 깊이 35 + 30).
- 같은 색의 전자식은 홀수, 열쇠식은 바로 다음 짝수 (예: 색 33 → 001/002).
- 색 순서는 독일어 이름 완전 알파벳 순: 33→1, 31→3, 22→5, 27→7, 25→9, 30→11, 28→13, 29→15, 35→17, 32→19, 36→21, 26→23, 24→25, 23→27, 34→29 (홀수 = 전자식 번호).

### 5-2. accessory-variants API (SOURCE 13lzs0_g8pri-.js:672~682)

```
GET {origin}/api/usm/accessory-variants?a=BZ%20002%20000
→ { variants: [ { artNum, ... }, ... ] }   배열이 아니면 "Malformed accessory-variants response"
```

- 응답을 `artNum`을 키로 하는 맵으로 저장한다. `safeVariant(품번)`이 그 항목을 돌려준다.
- 코드에서 쓰는 필드: `artNum`, `priceEur`, `priceChf`, `stock`, `deliveryTime`. 가격 두 개는 존재만 확인(값 미기록). 그 외 필드(이름, 색, 잠금 등)가 응답에 있는지는 코드로는 알 수 없다 (GUESS).
- `stock`은 장바구니 담기 전 재고 판정에 쓴다: 금고 항목 각각 `stock ≥ quantity`이면 빠른 배송 문구, 아니면 `deliveryTime`(또는 기본 `"6-8"`)로 납기 문구 (14x:38624~38650, SOURCE).
- 금고 가격은 `articleMap`에 합산하지 않고 `accessoryPriceChf/Eur`와 `accessoryWeight`에 **따로** 합산한다 (14x:22147~22150, SOURCE). 금고 줄의 `articleMap[BZ 002 …]` 항목은 `key`와 `artNum` 모두 `BZ` 품번이다.
- 장바구니에는 금고가 별도 `members[n].artNum` 번들 항목으로 넘어간다 (14x:39290~).
- 호환 크기가 아니면 구성에서 금고가 제거된다 (14x:36693, 37894).

### 5-3. 재고 API (SOURCE 14x:38406~)

```
GET {origin}/api/usm/stocks[?hash=<이전 해시>]  →  { hash, map: { <품번 "UH …"> : 재고수 }, ... }
```

- 구성 전체의 `articleMap`에서 `BZ 002 ` 로 시작하지 않는 모든 항목이 `artNum`을 갖고 `재고 ≥ quantity`이며 볼(`UH 058 000`)의 재고가 > 0이면 빠른 배송 판정(`Z.Avail.FAST`), 아니면 일반 (SOURCE 14x:21311~21350).

## 7. 우리가 구현할 때 필요한 최소 사양

1. **부품 정의 테이블**: `{internal_key(5자리), name_de/en/fr, weight_g, category, spec}`. smow의 98개가 현재 구성기 사용분이다.
2. **색별 품번 테이블**: `{internal_key, color_id(22~36), supplier_part_no}`. 39 기본키 × 15색 = 585줄. 색 없는 부품은 `color_id = NULL`.
3. **치수→부품 매핑 테이블**: `{table, dim1, dim2, hand, internal_key}`. 22개 표를 하나로 합치려면 `table` 컬럼(예: `panel_closed`, `panel_perforated`, `panel_short`, `shelf_divider`, `door`, `ext_shelf`, `drawer_front`, `drawer_side`, `rail`, `bracket`)을 둔다.
4. **단가 테이블**: `{internal_key, currency, net_price, valid_from}`. 색별 차이가 있으면 `color_id` 추가.
5. **금고 조합표**: `{depth, color_id, lock, part_no}` 60줄 + 품번별 가격·재고·납기는 별도 연동.
6. **한계값 설정**: 3-3절의 상수 15개.
7. **수량 규칙 코드**: 칸의 이웃 유무(왼쪽 열, 아래 칸)에 따라 볼 8/4/2, 커넥터 24/16/10, 가로·세로 파이프 4/2, 깊이 파이프 4/2/1 등 4-1절 규칙. 바퀴 4가지 위치 규칙.
8. **검증 도구**: 표 로드 시 (a) 모든 `internal_key`에 가격이 있는지 (b) 색 있는 부품의 15색이 다 있는지 (c) 치수 조합 표에 빠진 조합이 있는지를 검사. smow 구현은 이것이 없어 `TypeError`/`NaN`이 날 수 있다.
9. **지원 범위 결정**: 접이문·인출문(+서랍)·금속 패널만 지원한다. 유리 패널, 유리 문, 음향 패널, 플립업 문은 smow도 미지원(예외)이다.
10. **총액 규칙**: 총액은 정수로 내림하는지(smow 동작) 반올림하는지 우리가 정한다.

## 8. 읽지 못한 것 · 불확실한 것

- **서버 쪽 전부.** 단가의 원천 마스터, 재고 API 내부, `/api/usm/articles/` 가 받은 `priceEur`를 서버가 재계산하는지, 응답 구조. 클라이언트 코드에는 없다.
- **accessory-variants 응답의 전체 필드.** 코드가 읽는 5개(`artNum`, `priceEur`, `priceChf`, `stock`, `deliveryTime`)만 확인.
- **`o*` 표의 일부 용도 해석.** 옆판에 구멍 패널(`o3`)을 쓰는 이유, 뒷면 수량이 `H.t`인 이유, 17.5×17.5 패널이 없는 이유는 코드로는 판단 불가(GUESS).
- **단가표에만 있는 6개 키** (`10731, 10737, 11205, 16170, 16174, 16634`)의 정체. 품번은 있으나 이름이 없다.
- **품번 616개의 빈 번호(일련번호 누락) 전수 검사.** 중복은 없음을 확인했으나 접두사별 연속성은 일부(UH 052)만 봤다.
- **`lU`(조립용 파이프 교체)의 열 분배 공식.** 호출 구조와 예외만 확인, 선택 로직(3개 간격, 마지막 열 처리)은 완전히 해독하지 못했다.
- **코드를 실행하지 않았으므로** 모든 표 값은 텍스트 읽기 결과다. 표를 변환하는 스크립트 검증(예: 616줄 JSON 변환 후 재대조)은 하지 않았다.
- **원본(압축) 청크**는 정리본과 동일 파일명이 존재하는 것만 확인했다. 정리본과 다르게 생긴 부분을 비교하지 않았다.
- **UI 쪽 허용 치수 목록**(칸 너비·높이 선택지)과 설정 화면 제약은 분석하지 않았다. 3-1의 5가지 길이는 기하 정의 키에서 도출한 것이다.
- 판매 가격·재고 값은 지시에 따라 의도적으로 문서에 옮기지 않았다.
