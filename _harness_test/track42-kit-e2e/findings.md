# Track 42 findings (kit defects met while building a real small site with the kit)

Written as they were met, before any fix. Each one names what was observed and where.

| # | Met at | Observed | Kind |
|---|---|---|---|
| K-1 | Planning gate, main document only | `plan-doc-check` PASSED with only the main document, the common rules, the lesson plan and the module plan present. None of the four deliverables (DB, screens, design, source) existed yet, and the trace table pointed at files that did not exist. Standing order O-05 (four deliverables as files) was not enforced by the gate the kit lists as C2 | gate gap |
| K-2 | Fresh headless session | The bundled command-line client answered «Not logged in» in a folder outside the app, so the supervisor's default command cannot start a session on this machine until the operator logs the client in. `nonstop.js` would count that as three sessions without progress and stop with NO_PROGRESS, without naming the cause | supervisor gap |
| K-3 | Screen planner reading its lessons | Inside the project folder `node scripts/coolhan.js field-lessons list` (the command the kit's own `CLAUDE.md` gives) failed with ENOENT: the tool looked for the registry under the project folder. The kit's fixed check C3 (`field-lessons check`) would have failed the same way once source existed | tool defect |
| K-4 | Kit install | `_workspace/_goal.md` records the installer's `--intent` text as `operator_command`, not the operator's own words | record gap |
| K-5 | Parallel planning | Two planners (screens, source) each referenced the other's error text keys while both were still writing; they converged only by messaging each other. The common rules fixed IDs and names but not which part owns the error-code list | process gap |
| K-6 | Integration review | All four mechanical gates passed (`plan-doc-check` with lessons, modules and required deliverables; `plan-check`; schema check 42/42; contrast 51/51) while a reviewing agent found 2 faults that block implementation and 9 that would cause defects: a unit whose test needs a file from a later unit, a contract that accepts values the schema rejects, a client rule that breaks login, a row layout that cannot fit 320px by arithmetic, three features with no recorded decision. The kit's ledger template names only the two scripts as the planning gate; the review step (standing order O-17) is not a row | process gap |
| K-7 | Test command | `node --test test/` fails on Node 24.15 (it needs a file glob); the main plan carried that command from the first draft and no gate ran it | plan defect, caught by review |
| K-8 | Second review of the plan | The plan had the first unit create a package file with `"type": "module"`. The kit launcher (`scripts/coolhan.js`) is CommonJS, so after that unit every fixed check, every gate and all three loop hooks of the project would have failed with «require is not defined in ES module scope». Nothing in the kit said so and no gate could see it | kit defect |
| K-9 | Second review of the plan | `parallel-plan.js` read only `files` (created) and ignored `edits` (changed). It put two units that edit the same route table in one wave | gate defect |
| K-10 | Both reviews | The review found faults in the first pass (2 blocking) and again after the fixes (1 blocking, introduced by nobody: present from the first draft and missed by the first review). One review pass is not enough to call a plan clean | process gap |
| K-11 | Backlog decomposition | The plan numbered its units `U-01` (the planning standard writes IDs with a hyphen: R-01, S-01). `completion-check` recognised only `U1`, read the 15-row backlog as «0/0 units» and would have reported NOT complete for ever; the stop hook and the supervisor both rest on that gate | gate defect |
