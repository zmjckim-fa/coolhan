대상: https://www.smow.de/konfigurator/usm/haller
분석일: 2026-11-04
방법: 페이지가 정상 로딩할 때 받는 공개 JS 14개·CSS 2개·구성 JSON 1개와 API 응답 2건(각 1회)을 내려받아 **읽기만** 했다. 실행·클릭·쿠키 동의·대량 호출은 하지 않았다. REA `analyze_javascript_application`은 구조 요약(Turbopack 번들이라 모듈 복원 0건)만 돌려주었고, 실제 로직은 prettier로 정리한 코드를 직접 읽어 확인했다.

표기: **[관찰]** 코드·응답에서 직접 읽음 / **[추정]** 관찰에서 이끌어 낸 판단 / **[미확인]** 읽지 못함.

## 0. 사용 범위 (중요)

- 이 문서는 우리 구성기를 설계하기 위한 **기능·구조 참고**다. smow의 코드, 이미지, 구성 JSON, 가격표, 재고 데이터는 우리 쪽에 복제하지 않는다. 내려받은 원본은 세션 임시 폴더에만 있고 저장소에는 넣지 않았다.
- 부품 규칙은 USM 제품 사양에서 나온 것이다. smow 코드의 규칙값은 **우리 규칙의 정답이 아니라 대조 후보**이고, 공급사 부품표·조립 규칙으로 확인해야 한다.

## 3. 가격 구성 엔진

### 3.1 원리 [관찰]
구성 전체를 훑어 칸마다 부품을 **수량으로 누적**하고(`articleMap`: 품번 → 수량·단가·무게), 마지막에 합산한다. 가격 = Σ(품번별 단가 × 수량). 단가표는 통화별 2벌(EUR·CHF)이고 부품 정의는 `{A: 품번키, W: 무게}`다.

### 3.2 칸 하나가 만드는 부품 (코드에서 읽은 규칙)
| 부품 | 수량 규칙 |
|---|---|
선반은 세로로 쌓인 칸의 **열(column)** 을 가로로 늘어놓은 구조다(`parts/B_조작_상태_로직.md`). 아래에서 "왼쪽 칸"은 왼쪽 열의 같은 높이 칸, "아래 칸"은 같은 열에서 바로 아래 칸이다. 앞서 이를 "행" 기준으로 풀어 쓴 설명은 뒤바뀌어 있어 정정했다. 부품 이름(볼, 파이프 등)은 코드에 변수명만 있어 **[추정]** 이다.

| 부품 | 수량 규칙 |
|---|---|
| 연결구(볼로 추정, `oB`) | 왼쪽 칸과 아래 칸이 둘 다 있으면 2, 둘 중 하나면 4, 없으면 8 |
| 깊이 파이프 | 같은 조건으로 1 / 2 / 4 |
| 폭 파이프 | 아래 칸이 있으면 2, 없으면 4 (폭 75는 별도 파이프 + 금속 패널 2~4) |
| 높이 파이프 | 왼쪽 칸이 있으면 2, 없으면 4 |
| 하울러 커넥터(`oV`) | 10 / 16 / 24 (같은 조건) |
| 측면·윗면·뒷면·아랫면 패널 | 면 구성(`panelConfiguration`)별로 치수 조합 표에서 품번 선택. 이웃이 이미 같은 면을 가지면 중복 계산하지 않는다 |
| 위로 여는 문 | 문 본체, 손잡이, 자물쇠 유무에 따라 부품 변형, 보조 부품 2종 × 2, 칸 폭·높이에 맞는 앞판 |
| 금속 확장 문 | 앞판, 확장 선반(깊이별), 손잡이, 자물쇠 변형, 좌우 레일(깊이별), 끝막이 좌우. 서랍 포함은 서랍 정면·측면 추가 |
| 다리 | 글라이드는 왼쪽 칸이 있으면 2, 없으면 4. 바퀴는 열 기준: 열이 1개면 일반 2+잠금형 2, 첫 열이면 1+1, 오른쪽 열에 같은 높이 칸이 있으면 2+0, 그 외 3+1 |
| 칸막이 선반, 금고 | 해당 부속 선택 시 추가 |
| 케이블 구멍 | 선택한 구멍 수만큼 추가요금 품목 |

### 3.3 구성 후처리 규칙 (한도 적용)
| 규칙 | 내용 |
|---|---|
| 무게·폭 한도 | 합계 무게 80 kg 초과 또는 폭 200 cm 초과 시, 지정한 파이프를 **조립용 슬롯 파이프**로 교체하고 그만큼 커넥터를 뺀다 |
| 높이 한도 | 높이 200 cm 초과 시 같은 방식으로 슬롯 파이프 교체 |
| 확장 문 정지구 | 확장 문이 여러 개면 세로 간격(17.5/25/35 단위)에 따라 정지구·스페이서 추가 |
| 고정 세트(앵커) | 확장 문이 있거나 깊이 25의 위로 여는 문이 있으면 필수. 그 외에는 높이(다리 4 포함)가 깊이별 한도(25→141.7, 35→198.4, 50→283.5) 이상이거나, 높이 구간별 무게 기준(110~145: 30 kg, 145~180: 50 kg, 180 이상: 70 kg)보다 **가벼우면** 필수(가볍고 높을수록 전도 위험). 바퀴 구성은 계산하지 않는다 |
| 확장 문 포함 | `purchaseAlways = true` → 항상 주문 제작(재고 판정 제외) |
| 배송 | 무게 15 kg 초과, 문 포함, 또는 치수가 택배 한도(50×75 cm)를 넘으면 택배 불가. 그 경우 무게·높이·폭이 한도를 넘으면 조립 서비스 "선택" |
| 조립비 | 순액 × 2% + 167.22689076 (부가세 19% 포함 시 약 199) |

### 3.4 금액 처리
- 부품 합계를 소수 4자리로 정리한 뒤 `부가세 포함 = floor(순액 × (1 + 세율))`, `순액 = 부가세 포함 ÷ 세율`로 되돌려 계산한다. **포함가가 원 단위 내림으로 정해지고 순액은 그에 맞춰진다** [관찰].
- 금고(Balzsafe) 같은 부속은 본체와 별도 합계(`accessoryPrice`)로 관리하고 `/api/usm/accessory-variants`에서 단가·재고·납기를 받는다 [관찰].
- 재고(`/api/usm/stocks`)는 품번 → 수량 맵과 해시를 받고, 해시가 바뀌면 다시 계산한다. 실패하면 몇 번 재시도 후 포기한다 [관찰].

## 4. 구성 JSON (`configs/35-23.json`)

- 키 40개 = `폭-높이-칸종류` 조합(폭 75·50·35 × 높이 35·25·17.5 × 종류 0~6, 일부만 존재). 이름의 `35-23`은 **깊이 35, 색 23(루비 레드)** 로 보인다 [추정].
- 값 = 미리보기 PNG(base64) + `config {w,h,d,a,pc,p}`. `pc`는 6면 각각 `{c: 색, t: 부품 종류}`, `p`는 위치 [관찰].
- 용도: 칸 선택 패널의 **썸네일 목록**. 3D 본 장면은 이 데이터가 아니라 코드로 그린다 [추정].

## 6. 구현 방법 요약 (우리 설계에 가져올 것)

1. **부품표 기반 계산을 화면과 분리**한다. 구성 데이터(칸 목록, 면 구성, 부속, 다리) → 부품표 → 금액 순서의 순수 함수로 두면 더리움 가격과의 대조 시험이 쉽다.
2. **한도 규칙을 데이터로 둔다.** 무게, 높이, 앵커 기준, 택배 한도, 조립비 계수는 설정 파일 하나에 모은다.
3. **3D는 코드 생성 + 모듈별 형상 병합**으로 만들고, 칸 종류는 면 구성 데이터에서 파생한다.
4. **재고와 납기는 별도 호출**로 받고 해시로 변경을 감지한다. 우리 쪽은 병행수입 주문 제작이 기본이라 재고 맵 대신 공급사 납기표를 쓴다.
5. **저장은 세션 단위 구성 + 썸네일**로 하고, 주문 연결 시 구성을 서버에 고정(주문 시점 스냅샷)한다.
6. **금액은 포함가 내림 방식 여부를 우리 정책으로 결정**한다(한국은 부가세 포함가 원 단위 표시가 일반적).

## 7. 읽지 못한 것·한계

- 부품 단가표와 품번표(`lc`, `lu`, `oP`, 파이프·패널 치수 조합 표) 전체는 읽지 않았다. 구조만 확인했다.
- 3D 부품 형상 코드(각 파이프·볼·패널의 치수와 곡면)와 드래그·충돌 계산 코드는 읽지 않았다.
- 실제 화면에서 조작해 본 결과(쿠키 동의 전이라 구성기 조작을 하지 않았다)와 계산 결과의 대조는 하지 않았다. 따라서 §3의 수량 규칙은 **코드 읽기 결과이고 실행 검증을 거치지 않았다.**
- 서버 쪽 규칙(장바구니 검증, 가격 재계산 여부)은 알 수 없다.
- 상표·형상 재현 관련 법률 판단은 이 문서의 범위 밖이다.

- 재고 폴링 주기 10초(`setInterval … 1e4`), 장바구니 전달은 `POST /api/usm/articles/`에 세션 ID와 **클라이언트가 계산한 `priceEur`** 를 보낸다. 서버 재검증 여부는 클라이언트 코드로 확인되지 않았다.
- 세션 ID는 `Math.random` 기반이라 비밀값으로 쓸 수 없다.
- **우리 쪽 필수 설계 결정:** 가격은 서버에서 다시 계산한다. 클라이언트 가격은 표시용으로만 쓴다.

**정정한 오류 (이 문서 앞부분)**
- `InstancedMesh` 사용이라고 쓴 것은 three.js 본체를 앱 코드로 오인한 것이었다.
- 칸 이웃을 "행" 기준으로 풀어 쓴 것은 뒤바뀌어 있었다. 선반은 세로로 쌓인 칸의 열을 가로로 늘어놓은 구조다.

**여전히 없는 것**
- 실제 화면에서 구성을 만들어 부품 목록·가격을 코드 분석과 대조하는 검증(칸 배치 조작이 성공하지 않았고, 번들 로컬 실행은 환경이 거부함).
- 서버 쪽 로직 전부(단가 원천, 재고 API, 금액 재검증, 품번 생성).
- 3D 파일(glTF·텍스처) 자체와 `35-23.json` 로딩 코드.
