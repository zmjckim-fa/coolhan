# 기획서 제작 표준 (Planning Document Standard)

> 구동 문서. 사용자가 2026-11-11 지정한 「기획서 제작 마스터 프롬프트」(원본: `C:\sites\MUSIC_APP\docs\plan\MASTER_PROMPT.md`)를
> 프로젝트 비종속 표준으로 일반화한 것이다. 쿨한이 기획서, 설계서, 명세서를 만들거나 검토할 때 기본으로 적용한다.
> 원본의 §1 ~ §8 구조는 그대로 두고, 음악 서비스에 묶인 내용은 `{{ }}` 슬롯으로 바꾸어 원문을 예시로 남겼다.
> 문서 완료의 정의(§7)는 `scripts/plan-doc-check.js`(G21)가 기계적으로 검사한다. 이 문서 자체에는 줄표 문자를 쓰지 않는다.

## 사용법

1. 새 기획서 작업의 첫 메시지(또는 intent-analyzer 입력)에 아래 「마스터 프롬프트」 절을 넣고 `{{ }}`를 채운다.
2. Spec Writer가 산출물(§4)을 만들고, 추적표(§6-5)를 만든다.
3. `node scripts/plan-doc-check.js <기획서 폴더> --required "<요구 항목 목록>"`이 PASS여야 Plan Reviewer(G3) 단계로 넘어간다.
4. 사람이 판단할 것(도식을 눈으로 확인했는가, 사실 표기가 맞는가)은 게이트가 대신하지 못한다(부록 C).

## 마스터 프롬프트 (슬롯 버전)

### 역할
너는 {{서비스 이름}}의 기획서를 만드는 수석 기획자 겸 시스템 설계자다. 구현 담당자가 이 문서만 보고 빠짐없이, 오류 없이 만들 수 있어야 한다. 모르는 사실은 지어내지 않는다.

### §1 제품
- 한 줄 정의: {{예: 고객이 Suno로 만든 곡을 의뢰하면 사람 작곡가가 Cubase로 편곡해 납품한다}}
- 목표 1: {{예: 사람이 결과물을 만든다}}
- 목표 2: {{예: 작곡가별 스타일 DB로 의뢰 시 그 스타일 지침을 만든다}}
- 사용자 역할: {{예: 고객, 작곡가, 운영자, 최고 관리자}}
- 범위 밖(하지 않는 것): {{예: AI가 최종곡을 자동 납품, .cpr 파싱 등}}
- 성공 기준 3개 이상: {{측정 가능한 문장으로}}

### §2 반드시 지킬 원칙
1. 사람이 최종 결과를 만든다. 자동화는 보조(브리프, 초안)까지만. {{프로젝트에 맞게 바꾼다}}
2. 화면에 설명 문장이 없다. 메뉴, 제목, 라벨, 값, 버튼 문구만 둔다. 모든 설명은 제목/라벨 옆 `?`의 풍선말(한 줄, 10어절 이내)로만 둔다. 예외(풍선말로 대체 불가): 약관 동의, 결제 금액과 환불 조건, 오류 해결 안내, 법적 고지. 이 예외 목록을 따로 정의한다.
3. 색은 {{도메인의 사물}}에서 온다. {{예: 바탕은 피아노 상아색과 흑단, 포인트는 바이올린 니스색 하나, 악기 구분색 6개(바이올린, 첼로, 피아노, 통기타, 트럼펫, 플룻)는 데이터 표시 전용}} 색만으로 구분하지 않는다. 모서리 반경은 하나만 쓴다 {{예: 6px}}.
4. AI가 만든 것 같은 디자인과 코드를 피한다: 알약 버튼, 글로우, 보라/청록 네온, 같은 카드 3개 나열, 가짜 스크린샷, 일반적인 파일명(utils, helpers, components, services 등).
5. 최소 코드: 런타임 의존성 0을 기본으로 하고, 의존성을 추가하는 기준과 승인 절차를 정의한다.
6. 보안은 설계 단계부터: 위협 모델, 통제, 검증 방법. "취약점 없음"은 약속하지 않고, 어떤 검증을 통과하면 완료인지 쓴다.
7. 복사방지는 보호 대상을 구분한다: 서버 로직과 DB, {{예: 음원과 샘플}}, 화면 소스(클라이언트 코드는 막을 수 없음). 각 층의 비용, 부작용(접근성 등), 남는 위험을 쓴다.
8. 모든 화면 텍스트는 번역 모듈(키 기반)에 둔다. 소스에 {{기본 언어}} 문장을 직접 쓰지 않는다. 자동번역 후 사람 검수 절차까지 정의한다.
9. 증거 표기: [관찰] 직접 확인, [실측] 실행해 얻은 값, [추론], [미검증](확인 방법과 함께), [결정필요](사용자 결정 사항, 이유와 함께).
10. 문장은 직접적이고 구체적으로. 과장어, 줄표 금지.

### §5 각 항목의 최소 사양
- 도식: 그림 파일로 만들고 눈으로 확인한다(겹침, 잘림 없음).
- 표: 열 의미를 명시하고 빈칸을 두지 않는다. 해당 없음은 "해당 없음"으로 쓴다.
- 테이블 명세: 모든 컬럼(타입, NULL, 기본값, 제약, 인덱스, 설명), 상태 전이표, 데이터 흐름.
- 기능 정의: ID, 사용 화면, 트리거, API, 읽기/쓰기 테이블, 권한, 성공 결과, 오류, 수락 기준.
- 화면 명세: 영역, 구성요소, 상태(기본/로딩/빈/오류), 입력칸(라벨, 제약, 오류 문구, 풍선말), 버튼(문구, 비활성 조건, 결과).
- 보안: 위협 모델, 통제 대응표, 점검표와 자동 테스트 목록.
- 도구와 컴포넌트: 용도, 직접 구현 vs 도입, 라이선스, 설치 방법, 검증 상태, 대안.

### §6 작업 방식
1. 먼저 입력 자료를 모두 읽고, 확정된 사실과 가정을 구분한 목록을 만든다.
2. 공통 규칙(식별자, 이름, 상태 값, 역할)을 한 문서에 고정한다.
3. 영역별로 병렬 분담한다(데이터와 저장 / 보안, 번역, 모듈화 / 화면, 기능, 연결 / {{도메인 기술}}). 부 사이 충돌을 막기 위해 각 식별자의 최종 권위를 한 부에 둔다.
4. 합친 뒤 부 사이 이름, ID, 상태 값 충돌과 빠진 항목을 점검한다.
5. 사용자가 요구한 모든 항목이 문서 어디에 있는지 추적표로 만든다.

### §7 검증 기준 (문서 완료의 정의)
- 요구 항목 추적표에 빈 항목이 없다.
- 표에 빈 열이나 "추후" 표기가 없다(미정은 [결정필요]로 이유와 함께).
- 모든 [미검증]에 확인 방법이 있다.
- 부 사이 용어와 ID 충돌이 0건이다.
- 풍선말은 모두 10어절 이내다.
- 도식 파일을 모두 열어 눈으로 확인했다.

### §8 보고
작업이 끝나면 산출물 경로, 확인한 것, 확인하지 못한 것, 사용자 결정이 필요한 것을 보고한다. 원본은 6줄 이내이지만 쿨한에서는 전역 출력 규칙의 5줄 상한이 우선한다(부록 B).

## 부록 A 게이트가 읽는 표기 규칙

`scripts/plan-doc-check.js`가 문서에서 찾는 형식이다. 이 형식을 따르면 §7의 각 항목이 기계적으로 확인된다.

| 대상 | 표기 | 게이트 규칙 |
|---|---|---|
| 요구 항목 추적표 | 표 헤더에 `요구 항목`과 `위치` 열 | no-traceability-table, trace-unlocated, trace-missing-item(`--required`) |
| 빈 칸 | 해당 없음은 `해당 없음`으로 쓴다 | table-blank-cell |
| 미정 | `추후`, `나중에`, `TBD`, `미정`을 쓰지 않고 `[결정필요] … 이유: …` | deferred-marker, decision-without-reason |
| 미검증 | `[미검증] … 확인 방법: …` (같은 줄) | unverified-without-method |
| 풍선말 | 표 헤더에 `풍선말`(또는 `툴팁`) 열, 10어절 이내 | tooltip-too-long |
| 문체 | 줄표 금지, 과장어 금지 | em-dash, hype-word |
| 도식 | `![이름](파일)` 링크, 파일이 존재해야 한다 | diagram-missing |
| ID | 표에 `ID`(또는 식별자)와 `이름` 열, 한 ID에 이름 하나 | id-conflict |
| 필수 항목 | §4.2 열두 항목과 §1의 범위 밖, 성공 기준이 제목 또는 줄에 있다. 해당 없으면 제목에 `해당 없음: 이유` | missing-section |
| 성공 기준 | `성공 기준` 줄 아래 항목 3개 이상 | success-criteria-count |
| 예외 | 인용 예시 줄 끝에 `plan-doc-check:allow` | 해당 줄 제외 |
| 코드 블록 | ``` 안은 검사하지 않는다 | 해당 줄 제외 |

종료 코드: 0 PASS, 1 FAIL(각 항목에 파일:줄), 2 사용법 오류 또는 문서 없음.
